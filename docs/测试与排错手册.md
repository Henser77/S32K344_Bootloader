# S32K344 Bootloader —— 完整手工测试步骤

> 适用固件：`D:\S32DS\WorkSpace\S32K344_Bootloader`
> 测试工具：创芯科技 USB-CAN-2C（经典 CAN，500 kbps）
> 所有帧发往 **`0x7E0`**，每帧 **8 字节**；响应来自 **`0x7E8`**

---

## 0. 前置检查（只需要设置一次）

### 0.1 CT 里必须打开的四项配置（缺一不可）

```
C40_Ip → MemGeneral：
  ☑ Mem ECC Enable Check     ← 失效 Flash 控制器的预取缓冲
  ☑ Erase Verification       ← 擦完自动查空（判据可信）
  ☑ Program Verification     ← 写完自动校验
  ☑ Synchronize Cache        ← 失效 CPU 的 D-Cache

Cache Ip 组件：
  ☑ 启用                      ← 让 CACHE_IP_IS_AVAILABLE = STD_ON
```

对应代码里的宏（`generate/include/C40_Ip_Cfg.h` 和 `Cache_Ip_Cfg_Defines.h`）：

| 宏 | 必须是 |
|---|---|
| `C40_IP_ECC_CHECK` | `STD_ON` |
| `C40_IP_ERASE_VERIFICATION_ENABLED` | `STD_ON` |
| `C40_IP_PROGRAM_VERIFICATION_ENABLED` | `STD_ON` |
| `C40_IP_SYNCRONIZE_CACHE` | `STD_ON` |
| `CACHE_IP_IS_AVAILABLE` | `STD_ON` |

**为什么这四项缺一不可**

本工程同时满足两件事：D-Cache 是开着的，且 MPU 把 Program Flash 配成了
`Write-Back/Allocate`（可缓存）。所以 CPU 读到的 Flash 内容是**缓存副本**，
Flash 被擦写后 CPU 并不知道。这四项分别负责：

| 开关 | 管的是 |
|---|---|
| `Mem ECC Enable Check` | Flash 控制器内部的**预取缓冲** |
| `Synchronize Cache` + `Cache Ip` | CPU 的 **D-Cache** |
| `Erase Verification` | 擦除结果**是否可信**（驱动自己查空）|
| `Program Verification` | 写入结果**是否可信**（驱动自己校验）|

> 这四项打开后，`C40_Ip` 在擦除完成时会先失效缓存再查空，在每次读之前
> 也会先失效缓存 —— 所以 `Mcal/fls.c` 里**不需要**任何手写的缓存维护代码。

### 0.2 代码里保持的处理

| 位置 | 内容 | 作用 |
|---|---|---|
| `Mcal/fls.c` → `Fls_Erase` | 擦除判据用驱动的 `Erase Verification`，只在返回 `ERROR_BLANK_CHECK` 时重擦（最多 3 次）| 擦除偶发失败允许重试 |
| `Mcal/fls.c` → `Fls_WaitEraseDone` / `Fls_WaitWriteDone` | 两阶段等待：先等 `MCRS.DONE` 清零确认硬件开工，再等完成 | 防御性措施，避免读到上一次残留的完成标志 |
| `main()` | **显式调用 `Fls_Init()`** | 不能依赖调试代码去初始化模块（曾经把 `Fls_Init` 藏在自检里，自检一关 Flash 就从未初始化）|

## 2. UDS 测试流程（10 步）

**发帧时注意：每一步先等到响应，再发下一步。**
S3 超时是 **2 分钟**，不用赶。

---

### 第 1 步：进扩展会话

**发送：**
```
02 10 03 00 00 00 00 00
```

**期望收到：**
```
06 50 03 00 32 01 F4 CC
```

<details>
<summary>这帧是什么意思</summary>

- `02` = SF，后面 2 字节有效数据
- `10 03` = DiagnosticSessionControl，子功能 0x03（扩展会话）
- `50 03` = 肯定响应
- `00 32` = P2 = 0x0032 = 50 ms
- `01 F4` = P2* = 0x01F4 × 10 ms = 5000 ms
- `CC` = 填充字节

</details>

**串口会打印：** `Session=DEFAULT → EXTENDED` 之类

---

### 第 2 步：请求安全种子

**发送：**
```
02 27 01 00 00 00 00 00
```

**期望收到：**
```
06 67 01 SS SS SS SS CC
```
（`SS SS SS SS` 是 4 字节随机种子）

**串口会打印一行可以直接复制的密钥帧：**
```
[debug] >> SEND: 06 27 02 XX XX XX XX CC
```

> ⚠️ **只点一次 `27 01`**。重复请求不会换种子（已处理），但一次就够。

---

### 第 3 步：发送密钥

**发送**（照抄串口那行，`XX XX XX XX` 是 4 个字节）：
```
06 27 02 XX XX XX XX CC
```

**期望收到：**
```
02 67 02 CC CC CC CC CC
```

**串口应显示：** `security=2`（2 = 已解锁）

<details>
<summary>密钥算法</summary>

```
seed = (计数器 × 0x9E3779B1) ^ 0xA5A5A5A5
key  = (seed ^ 0x5A5A5A5A) + 0x12345678
```
诊断仪不需要自己算 —— 串口会直接打印出来。

</details>

---

### 第 4 步：切到编程会话

**发送：**
```
02 10 02 00 00 00 00 00
```

**期望收到：**
```
06 50 02 00 32 01 F4 CC
```

**串口应显示：** `session=1 security=2`

> `session: 0=default 1=programming 2=extended`
> `security: 0=locked 1=seed-sent 2=UNLOCKED`

---

### 第 5 步：擦除 App 区（`0x31 01 FF00`）

**发送：**
```
04 31 01 FF 00 00 00 00
```

**期望收到两帧：**

**① 立刻：**
```
03 7F 31 78 CC CC CC CC
```
（`7F 31 78` = "正在处理，请等待"）

**② 然后（约 0.5 ~ 10 秒后）：**
```
05 71 01 FF 00 00 CC CC
```
（`71 01 FF 00 **00**` —— 最后一个 `00` = 成功）

**串口会打印：**
```
[debug] 0x31 took ???? ms, erased 128 sectors (144..271), spin ?????, retries ?
```

**判断标准：**

| 字段 | 期望 | 说明 |
|---|---|---|
| `erased` | **128** | 1 MB = 128 个 8 KB 扇区 |
| `retries` | 0 ~ 几十 | >0 表示重擦兜底在工作，正常 |
| `took` | < 5000 ms | 超过 5 秒会触发诊断仪 P2* 超时 |

---

### 第 6 步：请求下载（`0x34`）—— **两帧**

**第一帧（11 字节命令，需要多帧传输）：**
```
10 0B 34 00 44 00 50 00
```

**期望先收到流控帧：**
```
30 00 00 CC CC CC CC CC
```

**收到流控帧后，立刻发第二帧（剩余数据）：**
```
21 00 00 00 00 10 CC CC
```

**期望收到：**
```
04 74 20 04 02 CC CC CC
```

<details>
<summary>这帧是什么意思</summary>

- `34` = RequestDownload（请求下载）
- `00` = dataFormatIdentifier（不压缩、不加密）
- `44` = addressAndLengthFormatIdentifier（地址 4 字节，长度 4 字节）
- `00 50 00 00` = 地址 `0x00500000`（App 区起始）
- `00 00 00 10` = 长度 `0x10` = 16 字节
- 响应 `74` `20` = maxNumberOfBlockLength `0x0020`（后续每块最多 32 字节）
- `04 02` = lengthFormatIdentifier `0x04` + 保留

</details>

---

### 第 7 步：传输数据（`0x36`）—— **三帧**

**第一帧：**
```
10 12 36 01 11 22 33 44
```
（`36` = TransferData，`01` = 块序号 1，后面是数据）

**收流控帧后，第二帧：**
```
21 55 66 77 88 99 AA BB
```

**再收流控帧后，第三帧：**
```
22 DD EE FF 12 34 CC CC
```

**期望收到：**
```
02 76 01 CC CC CC CC CC
```
（`76` `01` = 块序号 1 接收成功）

> 实际写入 Flash 的 16 字节是：`11 22 33 44 55 66 77 88 99 AA BB DD EE FF 12 34`

---

### 第 8 步：结束传输（`0x37`）

**发送：**
```
01 37 00 00 00 00 00 00
```

**期望收到：**
```
01 77 CC CC CC CC CC CC
```

---

### 第 9 步：CRC 完整性校验（`0x31 01 FF01`）

**发送：**
```
04 31 01 FF 01 00 00 00
```

⚠️ **注意：这一步的响应是 9 个数据字节，超过单帧 7 字节的上限，会分两帧发，
中间需要诊断仪发一个流控帧。** 这是整份流程里**唯一**一个"ECU 主动分多帧"的地方。

**① 立刻收到"请等待"：**
```
03 7F 31 78 CC CC CC CC
```

**② 接着收到首帧（FF）：**
```
10 09 71 01 FF 01 00 F8
```
（`10 09` = 首帧，总长 9 字节；`F8` 是 CRC 的第 1 个字节）

**③ 你需要发流控帧（CTS = 继续发送）：**
```
30 00 00 CC CC CC CC CC
```

**④ 然后收到连续帧（CF）：**
```
21 91 41 F2 CC CC CC CC
```
（`21` = 连续帧，序号 1；后面 3 个字节是 CRC 的剩下 3 个字节）

> **本测试用例的期望 CRC32 = `0xF89141F2`，传输顺序 `F8 91 41 F2`。**
> 这个值可以用 Python 独立验证：
> ```python
> import zlib
> data = bytes.fromhex("112233445566 7788 99AA BBDD EEFF 1234".replace(" ",""))
> print(hex(zlib.crc32(data)))     # -> 0xf89141f2
> ```

**拼起来的完整响应是：**
```
71 01 FF 01 00 <CRC 4字节>
```

**判断标准：**
- 第 5 个字节（`00` 那个位置）**是 `00` = Flash 内容与传输的 CRC 一致** ✅
- 如果是 `01` = 不一致（数据被破坏）

> 这一步现在有真正的意义了 —— 因为读已经可靠（D-Cache + ECC 两个都修了）。

---

### 关于"多帧"的两个方向（别搞混）

| 方向 | 谁分多帧 | 谁发流控帧 |
|---|---|---|
| **你 → ECU**（第 6️⃣7️⃣ 步的请求）| 诊断仪 | **ECU 发** `30 00 00 ...` |
| **ECU → 你**（第 9️⃣ 步的响应，9 字节）| ECU | **你发** `30 00 00 ...` |


---

### 第 10 步：复位（`0x11 01`）

**发送：**
```
02 11 01 00 00 00 00 00
```

**期望收到：**
```
02 51 01 CC CC CC CC CC
```

**然后芯片会通过 `AIRCR` 复位** —— 串口会重新打印开机信息。

> 目前只实现了"回响应 + 复位"，还没有"跳转到 App"。
> 跳转功能是下一步要做的（App 需要重新链接到 `0x00500000` 并做 VTOR 重定位）。

## 4. 故障排查

### 4.1 通用技巧

**任何时候拿不准，先发这个保活帧**（会刷新 S3 计时器，不影响状态）：
```
01 3E 00 00 00 00 00 00
```
→ 期望 `01 7E CC CC CC CC CC CC`

**串口永远是第一手信息** —— 每帧收发都有打印：
```
RX 0x7E0 [8] 04 31 01 FF 00 00 00 00
[UDS] req SID=0x31 len=4
      31 01 FF 00
      session=1 security=2  (...)
```

### 4.2 负响应码（NRC）对照

收到 `7F <SID> <NRC>` 时：

| NRC | 含义 | 常见原因 |
|---|---|---|
| `10` | generalReject | 请求格式不对 |
| `11` | serviceNotSupported | 该 SID 未实现 |
| `12` | subFunctionNotSupported | 子功能号不对 |
| `13` | incorrectMessageLengthOrInvalidFormat | 长度字段不对 |
| `22` | conditionsNotCorrect | **会话不对**（比如没进编程会话就擦除）|
| `24` | requestSequenceError | **顺序不对**（比如没 `0x34` 就发 `0x36`）|
| `31` | requestOutOfRange | **地址/长度超范围**（比如擦除 BLOCK_0）|
| `33` | securityAccessDenied | **没解锁** |
| `35` | invalidKey | **密钥算错了** |
| `36` | exceedNumberOfAttempts | 连续 3 次密钥错误 → 需要重新上电 |
| `37` | requiredTimeDelayNotExpired | 密钥错误后等 10 秒 |
| `78` | responsePending | **正常**，表示"还在处理" |
| `7E` | subFunctionNotSupportedInActiveSession | 当前会话不支持该子功能 |
| `7F` | serviceNotSupportedInActiveSession | 当前会话不支持该服务 |

### 4.3 常见现象

| 现象 | 原因 | 处理 |
|---|---|---|
| 第 5 步擦除瞬间返回（几毫秒）| `Fls_Erase` 的读回验证没生效 | 检查 `Mcal/fls.c` 里 `Fls_IsSectorBlank` 是否被调用 |
| 擦除后 `retries` 很大（接近 384）| 某扇区始终擦不干净 | 检查 Flash 硬件/供电 |
| 自检 `readback : STALE` | D-Cache 失效代码被删了 | 检查 `Fls_Read` 里是否调用 `Fls_InvalidateDCache` |
| 自检 `blank : FAIL` | 同上 或 ECC check 被关了 | 检查 CT 的 `Mem ECC Enable Check` |
| `0x36` 返回 `7F 36 24` | 没先发 `0x34` | 按顺序重来 |
| `0x36` 返回 `7F 36 13` | 数据长度超过 0x0402 | 每块不要超过 1026 字节 |
| `S3 timeout -> session back to DEFAULT` | 超过 2 分钟没发东西 | 重发保活帧或重新从第 1 步开始 |
| 收不到 `30 00 00` 流控帧 | 首帧的 PCI 长度写错 | 检查 SF/FF 的长度字段 |
| 响应 ID 不是 `0x7E8` | CAN 过滤器配错 | 检查 `src/main.c` 的 `Boot_CanRxCallback` |

### 4.4 需要重新开始的信号

出现下面任一情况，从头（第 1 步）再来：

- 串口出现 `S3 timeout -> session back to DEFAULT`
- 收到 `7F xx 22`（conditionsNotCorrect）
- 收到 `7F 27 36`（密钥尝试次数超限）→ **需要断电重启**
- 收到 `7F 27 37`（请求太频繁）→ 等 10 秒

## 6. 内存分区（重要参考）

```
0x00400000 ~ 0x004FFFFF   BLOCK_0  ← Bootloader（代码所在地，擦写禁区）
0x00500000 ~ 0x005FFFFF   BLOCK_1  ← App 区（刷写目标）
0x00600000 ~ 0x006FFFFF   BLOCK_2  ← 参数区
    0x00600000 ~ 0x00601FFF          升级标志 / 期望 CRC
    0x00602000 ~ 0x00603FFF          Flash 自检测试扇区
0x00700000 ~ 0x007CDFFF   BLOCK_3  ← 可用
0x007CE000 ~ ...          HSE 保留区（禁止触碰）
```

**RWW（Read-While-Write）只在跨 Block 时有效** —— 所以 Bootloader 在 BLOCK_0、App 在 BLOCK_1，
擦写 App 区时 CPU 仍能从 BLOCK_0 取指，不需要把擦写代码搬到 RAM。

## 7. 这次踩过的坑（最终结论版）

> 下面这节是**事后复盘**，不是当时的想法。当时的判断有好几处是错的，
> 保留错误版本反而会误导以后的人，所以这里只写**最终站得住的结论**。

### 7.1 真正的根因只有一个：缓存

本工程同时满足两件事：

1. `system.c` 使能了 D-Cache（编译参数带 `-DD_CACHE_ENABLE`）
2. `system.c` 的 MPU 表把 Program Flash 配成 `Write-Back/Allocate`（**可缓存**）

于是 CPU 读到的 Flash 内容是**缓存副本**，而 Flash 控制器擦/写之后
**CPU 的缓存不会自动失效** → 再读同一地址就拿到擦写之前的旧数据。

**症状极易被误判成"擦除没生效"**：

```
擦除 → 读回仍是写入时的数据 0x11 0x12 ...
直接指针读同一地址 → 也是 0x11（同样经过 CPU 缓存）
但立刻再擦一次只用 0.26 ms（和擦空扇区一样快）
    → 硬件认为扇区已经空了 → 第一次擦除其实成功了 → 问题在读
```

### 7.2 正确的解法：四个 CT 开关，一行代码都不用写

| 开关（CT 里）| 宏 | 管什么 |
|---|---|---|
| `Mem ECC Enable Check` | `C40_IP_ECC_CHECK` | Flash 控制器内部的**预取缓冲** |
| `Synchronize Cache` | `C40_IP_SYNCRONIZE_CACHE` | CPU 的 **D-Cache** |
| `Cache Ip` 组件启用 | `CACHE_IP_IS_AVAILABLE` | 提供 `Cache_Ip_InvalidateByAddr` |
| `Erase Verification` | `C40_IP_ERASE_VERIFICATION_ENABLED` | 擦除结果**是否可信** |
| `Program Verification` | `C40_IP_PROGRAM_VERIFICATION_ENABLED` | 写入结果**是否可信** |

打开后，`C40_Ip` 内部的调用链是：

```
C40_Ip_Read
   └─ Cache_Ip_InvalidateByAddr()          ← 每次读之前失效 D-Cache

C40_Ip_MainInterfaceSectorEraseStatus
   └─ C40_Ip_Compare()                      ← 内建查空
        └─ Cache_Ip_InvalidateByAddr()      ← 查空前先失效 D-Cache
```

**验证方法**：反汇编确认有 `bl` 指令真的在调，而不是"编译进去了但没人用"。

### 7.3 我在过程中犯的四个判断错误（教训）

| # | 错误判断 | 为什么错 | 怎么才能早点发现 |
|---|---|---|---|
| 1 | "擦 8KB 不可能只要 0.25 ms，一定是假完成" | **擦已经空白的扇区本来就快几十倍**。用错误的先验否定了真实观测 | 先测"擦有数据的扇区"和"擦空扇区"的正常耗时，建立基线 |
| 2 | "`MCRS.DONE` 有残留导致假完成" | 无法证实。观测差异用"空白/有数据"就能完整解释 | 一次只改一个变量，别在多个假设上同时动手 |
| 3 | "`MCRS.PEG` 位不清零导致连续擦除假成功" | 同样无法证实 | 同上 |
| 4 | **"写入校验失败 → 关掉校验"** | 校验读到的旧数据是**缓存**造成的，是校验**发现**了问题，不是校验**造成**了问题 | **永远不要拆掉报警器去修故障** |

### 7.4 最根本的教训

**验证工具本身坏了，比被测对象坏了更难查。**

CAN / CanTp / Dcm 是**无状态**的：发一帧、收一帧、对错立刻知道。
Flash 是**有状态**的：写下去就留着，错了会潜伏。

而验证 Flash 的唯一手段是**读**，读又被两层缓存污染 ——
**等于用一个坏了的温度计去测体温，然后反复怀疑病人有没有发烧。**

### 7.5 方法论

1. **能"对比"就不要"推断"** —— 而且要对比**不同层**的东西
   （CPU 视角的"读" vs 硬件视角的"再擦一次要多久"），
   而不是"看起来不同"的两个接口（`raw ptr` 和 `C40_Ip_Read` 共享同一级缓存）。
2. **让失败点自己报位置** —— 例如 `BlankCheck` 报出"第一个非 0xFF 字节的地址和值"，
   比连续几轮猜时间、猜计数有效得多。
3. **先查厂商有没有现成机制**，再造轮子。
   本项目手写过 `DCIMVAC` 循环和擦后读回校验，最后全部删掉 —— 都是多余的。

## 8. 跳转 App 的验证步骤

### 9.1 前提

- Bootloader 已烧录（`0x00400000` 段）
- App 已烧录（`0x00500000` 段）——用 App 工程自己直接烧，它的链接地址就是 `0x00500000`

> ⚠️ 烧 Bootloader 时**不能勾"擦除整片 Flash"**，否则会把 App 擦掉。

### 9.2 路径 A：用 UDS 刷写（真实流程）

```
1.  10 03           扩展会话
2.  27 01           请求种子
3.  27 02 <key>     发密钥
4.  10 02           编程会话
5.  31 01 FF00      擦除 App 区（会先置 AppValid=0）
6.  34 ...          请求下载
7.  36 ...          传输数据（很多块）
8.  37              结束传输
9.  31 01 FF01      CRC 校验 → 一致时自动写 AppValid=1
10. 11 01           复位 → 自动校验通过 → 跳 App
```

### 9.3 路径 B：用调试器烧 App + `0xFF02` 认账（快速验证跳转）

适合"只想确认跳转能不能成功"，不用发几千帧。

```
1. App 工程：直接烧录到 0x00500000
2. Bootloader 工程：烧录
3. 上电，串口应打印：
       App 校验 : 参数区没有有效账本（从未刷写过 / 已被擦除）
       [启动] 留在 Bootloader，等待诊断仪刷写
4. CAN 发这 5 帧：
       02 10 03 00 00 00 00 00
       02 27 01 00 00 00 00 00
       06 27 02 XX XX XX XX CC        （照抄串口打印的那帧）
       02 10 02 00 00 00 00 00
       07 31 01 FF 02 00 00 80 00     ★ 信任 App 区，长度 0x8000 = 32KB
5. 期望响应：
       03 7F 31 78 CC CC CC CC        先"请等待"
       09 71 01 FF 02 00 <CRC 4字节>  状态 00 = 记账成功
6. 发 02 11 01 00 00 00 00 00 复位（或断电重启）
7. 串口应打印：
       App 校验 : 向量表 SP=0x20020000  PC=0x00500421
       App 校验 : CRC 一致（0x????????，32768 字节）→ 可以跳转
       [启动] App 校验通过，准备跳转到 0x00500000
       [启动] 已停止 CAN 控制器，即将跳转...
       ########################################
       #        我 是 A p p                   #
       ########################################
       [App] 心跳 0 （我还在跑）
```

### 9.4 失败时怎么查

| 现象 | 原因 | 检查 |
|---|---|---|
| 串口写"参数区没有有效账本" | `0xFF02` 没发或失败 | 看 `71 01 FF 02` 的状态字节 |
| 写"账本标记 App 无效" | 上次 `0xFF00` 擦除后没走完 | 重新走完整流程 |
| 写"初始栈指针不在 RAM 范围" | App 向量表位置不对 | App 的链接脚本是否改成了 `0x00500000`、是否 `DISCARD` 掉了 `.boot_header` |
| 写"复位向量不在 App 区内" | App 的 AppSize 传小了 | `0xFF02` 的长度参数是否 ≥ App 镜像大小 |
| 写"CRC 不一致" | App 区内容和账本不符 | App 被改过 / 烧写不完整 |
| 跳过去了但串口没输出 | App 没初始化 UART，或波特率不同 | App 的 `Uart_Init` 是否调用；`APP_STANDALONE_INIT` 是否需要打开 |
| 跳过去后立刻 HardFault | VTOR 没设，或向量表地址不对 | App 的 `main` 第一行是否设了 `VTOR = 0x00500000` |

### 2026-10-25  ⭐⭐⭐ 最有价值的一次排查：CanTp 时间基准的并发竞态

**这是整个项目里最隐蔽、也最值得记住的 bug。它的排查过程比结论更有价值。**

#### 现象

**阶段一（v1.8）**：刷写能成功，但**过程有卡顿**，上位机日志偶尔出现
"块 0x01 超时，重试第 1 次…"，重发之后就过了。
当时以为是 CAN 时序问题，用"小块（256 字节）+ 2 ms 帧间隔 + 失败重试 3 次"压住了。

**阶段二（v1.10，只是把逐帧打印关掉）**：刷写**必然失败**，卡在第 2 块：

```
[CanTp] 传输中止：接收超时 N_Cr（对端不再发连续帧了）
        已收到 34 / 258 字节
[CAN] 收 312 帧（过滤掉 0）/ 发 18 帧（失败 0）
```

#### 关键推理（这一步是破案的转折）

```
收 312 帧      -> CAN 帧全部到了 CanIf（6 次尝试 x 37 帧 + 擦除等）
只拼到 34 字节 -> = 首帧 6 字节 + 4 个连续帧
中止原因是 N_Cr(超时)，而不是 RX_SEQ(序号错)
```

于是查 `CanTp_HandleConsecutiveFrame` 的两个分支：

```c
if (CanTp_RxState != CANTP_STATE_RX_WAIT_CF) return;      /* 静默忽略 */
if (sn != CanTp_RxSN) { CanTp_Abort(RX_SEQ); return; }    /* 序号错 */
```

**中止原因是 N_Cr 而不是 RX_SEQ，说明第 5 帧起走的是第一条**——
接收状态已经被 `CanTp_MainFunction` 里的 N_Cr 检查清成 IDLE 了。

#### 根因

`CanTp_GetTimeUs()` 内部是三组**读-改-写**共享变量：

```c
cyc      = CYCCNT;
deltaCyc = cyc - CanTp_LastCycles;
CanTp_LastCycles = cyc;                     // 读-改-写
CanTp_UsCounter   += deltaCyc / 160;        // 读-改-写
CanTp_UsRemainder += deltaCyc % 160;        // 读-改-写
```

而它被**两个上下文**同时调用：

| 调用点 | 上下文 |
|---|---|
| `CanTp_RxIndication`（第 526、577 行）| **CAN 中断** |
| `CanTp_Transmit` / `CanTp_MainFunction`（第 609、817、827 行）| **主循环** |

CAN 中断插在中间 → 主循环用"过期的旧值"覆盖中断刚写的新值 →
**`CanTp_UsCounter` 回退一点点**。

回退一点点的后果是灾难性的：

```
(uint32)(now - CanTp_RxTimerUs)      // now 比 RxTimerUs 小 1
    = 0xFFFFFFFF = 4,294,967,295 µs = 71 分钟
    > N_Cr (60 秒)
    -> 立刻超时 -> Abort -> 接收状态清成 IDLE
    -> 之后所有连续帧都被当作"孤立 CF"静默丢弃
```

#### 为什么"改日志"会让它必然失败

| 版本 | 主循环一圈 | `CanTp_GetTimeUs` 调用频率 | 撞车概率 |
|---|---|---|---|
| v1.8 | 约 1 ms（每帧打印 ~9 次阻塞式 Uart_Printf）| ~1000 次/秒 | 低 → 偶发 |
| v1.10 | 约 2 µs（不打印）| **~50 万次/秒** | 高 → 必然 |

**以前的"慢"一直在掩护这个 bug。日志瘦身不是元凶，它只是把地毯掀开了。**

#### 修复（两层）

**① 根因：时间基准加临界区**（`cantp.c`）

```c
static uint32 CanTp_GetTimeUs(void)
{
    ...
    primask = CanTp_EnterCritical();     /* mrs primask + cpsid i */
    ...三组读-改-写...
    value = CanTp_UsCounter;
    CanTp_ExitCritical(primask);         /* msr primask，恢复原值 */
    return value;
}
```

**为什么用 `msr primask` 而不是 `cpsie i`**：这个函数也可能在中断里被调用，
直接开中断是错的，必须恢复调用前的状态。

**② 兜底：所有超时比较防下溢**

```c
static boolean CanTp_ElapsedExceeds(uint32 Now, uint32 Start, uint32 Limit)
{
    uint32 elapsed = (uint32)(Now - Start);

    if (elapsed >= 0x80000000UL) return FALSE;   /* 看起来像"负数" → 时间没走 */
    return (elapsed > Limit) ? TRUE : FALSE;
}
```

替换了 4 处：`CanTp` 的 N_Cr / N_Bs，`Dcm` 的 S3 / 安全锁定延时。

#### 修复后的效果

- 刷写**一次通过，全程无卡顿**
- 上位机日志**不再出现任何"超时 / 重试"**
- 之前那些"偶发超时"全部消失

#### 这次排查的三条教训

**教训 1：中断和主循环共享的变量，读-改-写必须保护。**
不只是"计数器"这种明显的共享变量 —— `LastCycles` 这种"上次读到的值"
同样会被中断破坏，而且更隐蔽。

**教训 2：无符号减法做时间差，必须防下溢。**
`(uint32)(now - start) > TIMEOUT` 这个写法在时间基准出错时会变成
"已经过了 71 分钟"。加一句"差值必须在合理区间"是最便宜的保险。

**教训 3：性能优化会揭穿隐藏的并发缺陷。**
"把打印去掉让它变快"看起来纯赚，实际上改变了所有共享状态的
交互概率。**优化后出现的失败，往往不是优化本身写错了，
而是优化暴露了旧的错。**

### 2026-10-25  ⭐ 复位手段的三段式排查：AIRCR → MC_ME（钥匙顺序）

**同一个目标（`11 01` 真正复位）试了三次，失败原因各不相同，最后一条是"抄对了代码、抄错了顺序"。**

#### 第 1 段：ARM 标准做法（AIRCR）—— 芯片不支持

```c
*(volatile uint32*)0xE000ED0C = 0x05FA0004;   /* SCB->AIRCR.SYSRESETREQ */
```

这也是 CMSIS `NVIC_SystemReset()` 的做法，绝大多数 Cortex-M 上有效。

**实测**：写后读回 `0xFA050004`，SYSRESETREQ 位一直保持 1，但芯片不复位、PC 不变。
`MC_RGM` 里也没有"请求复位"的寄存器。

**结论**：S32K3 的系统复位不由 Cortex-M 的 SYSRESETREQ 承担。

#### 第 2 段：NXP 官方做法（MC_ME）—— 我抄错了顺序

查 NXP 驱动链条：

```
Mcu_PerformReset()                       Mcu.h:394
  -> Power_Ip_MC_RGM_PerformReset()      Power_Ip_MC_RGM.c:814
  -> Power_Ip_MC_ME_SocTriggerResetEvent()  Power_Ip_MC_ME.c:734
        MC_ME->MODE_CONF = FUNC_RST
        Power_Ip_MC_ME_TriggerModeUpdate():
            MC_ME->MODE_UPD = 1
            Power_Ip_MC_ME_WriteControlKeys():
                /* Starting the hardware processes */   ★ 关键注释
                CTL_KEY = 0x5AF0
                CTL_KEY = 0xA50F
```

我第一次实现时把钥匙写在**最前面**（"先解锁再配置"这个直觉）：

```c
CTL_KEY = 0x5AF0;        /* ← 先扣扳机，但枪膛是空的 */
CTL_KEY = 0xA50F;
MODE_CONF = FUNC_RST;    /* ← 然后才装子弹 */
MODE_UPD  = 1;           /* ← 没人再扣扳机了 */
```

**结果：配置躺在寄存器里，永远不会被执行。** 表现为"什么都没发生"。

#### 第 3 段：修正顺序 —— 成功

```c
MODE_CONF = FUNC_RST;    /* ① 要做什么 */
MODE_UPD  = 1;           /* ② 提交 */
CTL_KEY   = 0x5AF0;      /* ③ 启动（NXP: Starting the hardware processes）*/
CTL_KEY   = 0xA50F;
```

**实测复位成功。**

现在实现成两段式：先 `FUNC_RST`（功能复位，SRAM 保留），
不生效再试 `DEST_RST`（破坏性复位，SRAM 清空）。

#### 三条教训

**教训 1：移植别人代码时，"顺序"和"内容"一样重要。**
NXP 的代码我看到了、值也抄对了，但把三步的先后调了一下就完全失效。
注释里那句 `Starting the hardware processes` 已经写明了钥匙的作用，
我当时没把它当回事。

**教训 2：寄存器写进去 ≠ 硬件执行了。**
MC_ME 的写是"配置"，真正触发靠钥匙序列。这类"配置 + 触发"的寄存器对
（还有 Flash 的 `MCR.ERS` + `EHV`、CAN 的 `MCR` + 启动位）都必须分清。

**教训 3：失败了要区分"芯片不支持"和"我实现错了"。**
第 1 段和第 2 段的现象完全一样（什么都不发生），但性质完全不同：
一个是芯片行为，一个是我的顺序错。**不要因为一次失败就断定"这条路不通"。**
