## 一、全景：从上电到"跳 or 不跳"

```
芯片复位
   │
   ▼
Vector_Table.s  →  取 0x00400000 的 SP / Reset_Handler
   │
   ▼
startup_cm7.s   →  清 .bss、初始化 .data、调 main()
   │
   ▼
main()                    (src/main.c，42 行)
   │
   ▼
EcuM_Init()               (ecum.c:161 ~ 311)
   │
   ├─ 1  Clock / Port / IntCtrl
   ├─ 2  Det_Init
   ├─ 3  Uart_Init + 打印横幅
   ├─ 4  Fls_Init
   ├─ 4.5 BootParam_Load() + BootApp_Decide()   ★ 只判断，先不跳
   ├─ 5  Can_Init
   ├─ 6  CanIf_Init
   ├─ 7  PduR_Init
   ├─ 8  CanTp_Init
   ├─ 9  Dcm_Init
   ├─ 10 BootTrace_Init
   ├─ 11 CAN STARTED                            ★ 此刻才能收帧
   └─ 12 if (可以跳) { 启动窗口 1.5 秒 }
          ├─ 窗口内收到 UDS 请求 → 留在 Bootloader，返回
          └─ 没收到 → 停 CAN → BootApp_Jump() → 跑 App（不返回）
   │
   ▼
for (;;) { EcuM_MainFunction(); PduR_MainFunction(); BootTrace_MainFunction(); }
```

### 两条"活在 Bootloader 里"的路

| 路径 | 条件 | 之后 |
|---|---|---|
| **A. 上电时留下** | 7 步校验没过 | 一直留下，等诊断仪 |
| **B. 窗口后留下** | 校验过了，但 1.5 秒内有人发 UDS 请求 | 一直留下，等诊断仪 |

### 刷写过程中的一条特殊路

```
诊断仪发 11 01
   → Dcm 只置标志（不能当场复位，51 01 还没发出去）
   → EcuM_MainFunction 发现标志
       → 等 100 ms（让 51 01 发完）
       → 写 AIRCR 请求复位
       → 等 50 ms
           ├─ 芯片真复位了：走不到下面
           └─ 没复位（S32K344 就是这样）：
                 → 清标志
                 → BootApp_Decide() 重新校验 CRC
                     ├─ 通过 → 停 CAN → BootApp_Jump() → 立刻跑 App
                     └─ 不通过 → 留在 Bootloader
```

## 三、逐文件精读

### 3.1 `Library/crc32.c`（49 行）—— 最简单的，先建立信心

**三件事**：初始化值 → 逐位算 → 输出异或。

```c
#define CRC32_POLY        (0xEDB88320UL)   // 反射形式的多项式
#define CRC32_INIT        (0xFFFFFFFFUL)   // 初值
#define CRC32_FINAL_XOR   (0xFFFFFFFFUL)   // 输出异或
```

核心只有 8 行（`Crc32_Update`，27~42 行）：

```c
for (i = 0; i < Len; i++) {
    Crc ^= Data[i];                    // 把字节异或进最低字节
    for (bit = 0; bit < 8; bit++) {    // 逐位处理 8 次
        if (Crc & 1) Crc = (Crc >> 1) ^ POLY;   // 最低位是 1 → 右移后再异或多项式
        else         Crc = (Crc >> 1);          // 最低位是 0 → 只右移
    }
}
```

**逐位 vs 查表**：查表快 8 倍，但要 1 KB Flash 的表。这里 CRC 只在两个非热路径用（刷写逐块、上电一次），所以省 Flash。**两项实现只要多项式、初值、输出异或一样，结果完全相同** —— 将来换查表版不影响兼容性。

#### 两个必须注意的细节

1. **`Crc32_Update` 返回的是"中间值"，还没做输出异或**。
   所以 `Crc32_Calculate` 是 `Crc32_Final(Crc32_Update(CRC32_INIT, ...))` 两层。
   刷写时一边收一边算，最后再 `Crc32_Final` —— 这正是"分块累加"能用的原因。

2. **为什么要抽成独立模块**：`dcm.c`（刷写时算）和 `boot_app.c`（上电时算）**必须算出一模一样的值**。以前 dcm 里有一份私有实现，两处一旦有一个参数写错，就会出现"刷写说一致、上电说坏"，极难查。

**自测**：用 Python 验证一个已知值
```python
import zlib
hex(zlib.crc32(bytes.fromhex("11223344")))   # 应该和固件算出来的一样
```

### 3.2 `Application/boot_param.c`（185 行）—— 那个"账本"

**它回答一个问题**：App 区里那份固件，是完整的吗？

**光看"第一个字不是 0xFF"不够**。刷到一半断电时，App 区可能前半是新的、后半是 0xFF —— 看起来"有代码"，跳过去必然跑飞。只有 CRC 能发现。

#### 数据结构（`boot_param.h:67~77`）

```c
typedef struct {
    uint32 Magic;        // "SK3B" = 0x534B3342，区分"初始化过"和"空白 Flash"
    uint32 AppValid;     // 1 = 有效
    uint32 AppStart;     // 应为 0x00500000
    uint32 AppSize;      // 有效字节数
    uint32 AppCrc32;     // App 区的 CRC32
    uint32 Reserved0;
    uint32 Reserved1;
    uint32 StructCrc32;  // 前 28 字节的 CRC32 —— 必须是最后一个字段
} Boot_ParamType;
```

#### ★ 最重要的一条纪律：断电安全顺序

```
刷写流程                     AppValid      掉电后果
──────────────────────────────────────────────────────
擦 App 区之前                置 0          → 留在 Bootloader（安全）
擦除 / 写入 / 校验           保持 0        → 留在 Bootloader（安全）
全部成功、CRC 一致           置 1 + 写 CRC → 跳 App
```

**顺序反了会怎样**：先写"有效"再擦除，刷到一半掉电 → 账本说"有效" → 跳进半新半旧的 App → 跑飞，而且**再也连不上**（因为它跑飞了，不在 Bootloader 里）。

所以 `BootParam_SetInvalid()` 的注释里写着"**必须在擦除 App 区之前调用**"（`boot_param.h:111`），而 `dcm.c` 里擦除服务的开头就是它。

#### `BootParam_Write` 的四步（`boot_param.c:57~100`）

```c
① 算 StructCrc32 填进去（它覆盖前面的字段，所以必须最后算）
② Fls_Erase(参数扇区)        ← 整扇区擦，因为 Flash 只能 1→0
③ Fls_Write(32 字节)          ← Fls_Write 内部按 8 字节补齐
④ 回读校验（Fls_Read + 逐个字段比）
```

**为什么第 ④ 步还要回读**：Flash 写失败可能不报错（比如电压不够）。回读是唯一可靠的确认。而且 `Fls_Read` 内部会让 D-Cache 失效，读到的是真 Flash 内容，不会被缓存骗。

#### 为什么不做"双备份轮换"

那种方案能防"擦参数区时掉电导致账本全丢"。本工程用更简单也更安全的方式：**账本丢了 = App 无效 = 留在 Bootloader**。这个退路本身就是安全的 —— 最坏情况是"刷完的固件要重刷一次"，不是变砖。（`boot_param.c:13~16`）

#### 三个 API 的区别

| API | 谁调 | 干什么 |
|---|---|---|
| `BootParam_Load()` | 上电时 `EcuM_Init` | 从 Flash 读到 RAM，顺便校验 |
| `BootParam_IsStructValid()` | `BootApp_Decide` 第①步 | 魔数 + 结构 CRC 都对吗 |
| `BootParam_IsAppValid()` | `BootApp_Decide` 第②步 | 账本说 App 有效吗 |
| `BootParam_SetInvalid()` | `dcm.c` 擦除前 | 写"无效" |
| `BootParam_SetValid()` | `dcm.c` CRC 校验通过后 | 写"有效" + 长度 + CRC |

### 3.3 `Application/boot_app.c`（279 行）—— 最有面试价值的一个文件

三个函数：`BootApp_CalcCrc`（82~120）、`BootApp_Decide`（122~227）、`BootApp_Jump`（229~279）。

#### 7 步校验（任何一步失败都 `return BOOT_DECIDE_STAY`）

| 步 | 检查什么 | 行号 | 挡住的是什么 |
|---|---|---|---|
| ① | 账本结构有效（魔数 + 结构 CRC） | 132 | 空白 Flash / 账本被写坏 |
| ② | 账本说 App 有效 | 143 | 刷到一半断电 |
| ③ | `AppStart == 0x00500000` | 153 | 账本被写成别的地址 |
| ④ | `AppSize` 在 1 ~ 1 MB | 163 | 长度字段是垃圾值 |
| ⑤ | 向量表 `[0]`(SP) 落在 RAM 内 | 190 | App 区是空的（全是 0xFF → SP=0xFFFFFFFF） |
| ⑥ | 向量表 `[1]`(PC) 在 App 区内且 bit0=1 | 196 | 复位向量不可执行 |
| ⑦ | App 区 CRC32 与账本一致 | 215 | **刷到一半 / 写坏**（只有这一步能发现） |

**⑤⑥ 只读 8 个字节**，但能挡住绝大多数"跳进去跑飞"的情况，而且很快。

**⑦ 才是唯一能证明"内容完整"的检查** —— 前六步只能证明"看起来像代码"。

#### 两个容易忽略的小检查

```c
// ⑤ 的一部分：SP 必须 8 字节对齐（boot_app.c:42）
if ((Sp & 0x7) != 0) return FALSE;      // AAPCS 要求函数入口 SP 8 字节对齐

// ⑥ 的一部分：PC 的 bit0 必须是 1（boot_app.c:67）
if ((Pc & 0x1) == 0) return FALSE;      // Cortex-M 的 Thumb 地址 bit0 = 1
```

**为什么 PC 的 bit0 必须为 1**：Cortex-M 只支持 Thumb，向量表里的函数地址用 bit0 表示指令集。如果 bit0 = 0，说明这个"地址"根本不是合法入口（常见于读到了 0x00000000 或 0xFFFFFFFF）。

#### ★ 跳转的 5 步（`boot_app.c:229~279`）—— 面试高频

```c
sp = *(volatile uint32*)AppStart;         // App 的初始 MSP
pc = *(volatile uint32*)(AppStart + 4);   // App 的 Reset_Handler

__asm volatile ("cpsid i" ::: "memory");  // ① 关总中断
BOOT_REG_VTOR = AppStart;                 // ② SCB->VTOR = 0x00500000
// ③④⑤ 必须在同一段汇编里
__asm volatile (
    "msr  msp, %0 \n\t"                   // ③ 换栈
    "dsb          \n\t"                   // ④ 数据同步屏障（保证 VTOR 写生效）
    "isb          \n\t"                   //    指令同步屏障（清流水线）
    "bx   %1      \n\t"                   // ⑤ 跳到 App 的 Reset_Handler
    : : "r"(sp), "r"(pc) : "memory"
);
```

**四个"为什么"**：

1. **为什么要关总中断**：Bootloader 注册的中断处理函数地址在 Bootloader 区。不关的话，跳转后 App 还没准备好就来了中断，ISR 会跳到 Bootloader 的代码。
2. **为什么要设 VTOR**：不搬向量表，而是告诉内核"向量表在 AppStart"。这样 App 里发生中断时取到的是 App 自己的处理函数。
3. **为什么 `msr msp` 之后不能再访问内存**（最关键）：那一刻栈已经换成 App 的了，Bootloader 的局部变量全部失效。所以 `sp`/`pc` 必须**事先已经在寄存器里**，之后只能寄存器跳转。
4. **为什么 `dsb`/`isb` 不能省**：`dsb` 保证 VTOR 的写真正落到硬件；`isb` 清流水线，保证 `bx` 之后取到的是新位置的指令。

> **代码有个尾巴**：`BootApp_Jump` 最后有个 `for(;;)`。万一 App 的 Reset_Handler 返回了，停在这里比跑飞好 —— 跑飞触发 HardFault 死循环更难查。

**自测**：
- 如果第 ⑦ 步 CRC 一致但不做 ⑤⑥，可能跳过什么？
- 如果没有 `cpsid i`，跳转后第一个中断会去哪个地址取处理函数？
- 为什么 `sp`/`pc` 要在进入汇编**之前**读出来？

### 3.4 `Services/System/ecum.c`（437 行）—— 装配 + 调度 + 复位

三段：初始化（161~311）、启动窗口（127~159）、11 01 处理（375~437）。

#### 初始化顺序为什么是这样（文件头 1~33 行有完整理由）

两个关键约束：

1. **`Fls_Init` 必须在 `BootParam_Load` 之前** —— 读参数区要靠它。
2. **CAN 控制器必须最后 `STARTED`** —— 如果先上总线再初始化 CanTp/Dcm，初始化期间收到的帧会进来，而上面的模块还没准备好，出现"收到帧但没人处理"。

#### `EcuM_Fatal`（85~94）—— 为什么是死循环而不是复位

关键外设（时钟/Flash/CAN）坏了，程序没有意义继续跑。**复位会无限重启刷屏，反而看不到原因**；死循环至少把错误信息留在串口上。

#### 启动窗口（127~159）

```c
reqAtEntry = Dcm_GetRequestCount();     // 记下进入窗口时的请求数
start = DWT->CYCCNT;

while (还没到 1.5 秒) {
    CanTp_MainFunction();               // 必须跑主函数，否则收不到帧
    PduR_MainFunction();
    Dcm_MainFunction();
    BootTrace_MainFunction();

    if (Dcm_GetRequestCount() != reqAtEntry) return TRUE;   // 有人来找 → 留下
}
return FALSE;                            // 没人来 → 跳 App
```

**为什么用"请求计数"而不是"标志"**：计数可以让调用方先记下当前值，过一会儿看变没变 —— 不需要额外的"清标志"动作。

**这段循环里为什么必须跑那四个主函数**：Bootloader 是裸机轮询架构，没有任何后台线程。不跑 `CanTp_MainFunction` 就拼不出多帧消息，`Dcm` 也就永远不知道有人来过。

#### 第 12 步：跳还是留（297~310）

```c
if (JumpToApp) {
    if (EcuM_WaitBootHoldWindow() == FALSE) {
        Can_SetControllerMode(STOPPED);   // 跳之前停 CAN
        BootApp_Jump(BOOT_APP_START);     // 不返回
    }
}
```

**为什么跳之前要停 CAN**：App 会重新初始化 CAN 控制器。不停的话，控制器还带着 Bootloader 配的邮箱和中断使能，App 初始化时可能收到残留中断。

#### 11 01 的三段结构（375~437）

```
① Dcm_IsResetRequested()？
     第一次看到 → 记下 DWT 周期数，打印"100 ms 后重启"
② 过了 100 ms？
     → 写 AIRCR 请求复位（等 50 ms）
③ 复位没生效？（EcuM_RequestSystemReset 返回 TRUE）
     → 清标志（否则每圈重试 = 死机）
     → BootApp_Decide() 重新校验
         → 通过 → 停 CAN → 跳转 → 立刻跑 App
         → 不通过 → 留在 Bootloader
```

**为什么复位动作不能放在 Dcm 里当场做**：`51 01` 这条正响应还在发送队列里。当场复位，诊断仪收不到响应，会误判成"复位失败"。

**复位的实现走过三段弯路，值得记住**：

1. v1.3~v1.8 用 ARM 标准的 `SCB->AIRCR = 0x05FA0004`（也就是 `NVIC_SystemReset()` 的做法）。
   实测**无效**：读回 `0xFA050004`，SYSRESETREQ 位一直保持 1 但芯片不动。

2. v1.9/v1.12 改用 NXP 官方路径 **MC_ME**，但仍然无效 —— 因为**钥匙顺序写反了**：
   要先写 `MODE_CONF`、再写 `MODE_UPD`、**最后**写 `CTL_KEY` 钥匙序列
   （NXP 原话："Starting the hardware processes" —— 钥匙是"启动"那一下）。

3. v1.13 修正顺序后**实测复位成功**。现在先试 `FUNC_RST`（功能复位，SRAM 保留），
   不行再试 `DEST_RST`（破坏性复位）。

所以现在第 ③ 段（重新校验 + 直接跳转）是**兜底路径**，正常走不到。

**自测**：
- 如果 100 ms 的等待去掉会怎样？
- 为什么第 ③ 段要**重新** `BootApp_Decide()`，而不是用初始化时存的 `JumpToApp`？

### 3.6 `src/main.c`（42 行）—— 只剩三个调用

```c
EcuM_Init();                        // 一次性的初始化 + 上电决策
for (;;) {
    EcuM_MainFunction();            // CanTp + Dcm + 窗口/复位
    PduR_MainFunction();            // CanTp 拼好后 → 交给 Dcm
    BootTrace_MainFunction();       // 调试上报
}
```

**为什么没有 `Can_MainFunction_Read()`**：CAN 接收是**中断驱动**的（`CAN0_ORED_0_31_MB_IRQHandler` → `Can_IsrBridge` → `CanIf_RxIndication` → `PduR` → `CanTp`）。主循环只管"推进状态机"。

**为什么不能塞阻塞操作**：`CanTp` 的 `N_Bs`/`N_Cr` 超时是按主循环调用频率判定的。主循环被卡住几十毫秒（比如擦 Flash），拼装会暂停 —— 这是设计上接受的，因为擦写只在诊断仪主动请求时发生，那时对端也在等响应。

## 四、三个必须记住的设计点

### ① 断电安全顺序

> **任何会动 App 区的操作，都必须先把账本置"无效"，最后才置"有效"。**

掉电安全的本质量是：**任何时刻断电，板子都必须停在"可救援"的状态**（Bootloader），而不是"账本说有效但内容是坏的"。

### ② 宁可留在 Bootloader，绝不冒险跳

7 步校验里**任何一步失败都 `return BOOT_DECIDE_STAY`**。没有任何"猜一下"的分支。

代价：App 只是轻微损坏时会多刷一次。
收益：永远不会跳进坏固件跑飞，导致**诊断仪再也连不上**。

### ③ 跳转的最后 5 步之间不能插入任何代码

```
cpsid i  →  VTOR  →  msr msp  →  dsb/isb  →  bx
```

一旦 `msr msp` 执行，Bootloader 的栈就没用了 —— **这之后只能寄存器跳转，不能再访问内存**。

## 五、常见误解澄清

| 误解 | 事实 |
|---|---|
| "S32DS 烧录是全擦" | **不是**。只擦镜像覆盖到的扇区。实测烧 Bootloader 只擦 `0x400000~0x413FFF`（10 个扇区 80 KB），App 区和参数区完全没碰 |
| "`11 01` 会复位芯片" | **在 S32K344 上不会**。写 AIRCR 被"接受但不生效"。v1.7 的做法是"复位失败就重新校验并直接跳转 App" |
| "App 区第一个字是 0xFF 就说明没刷过" | 不够。刷到一半断电时前半可能是新的。**只有 CRC 能判断** |
| "账本只要魔数对就行" | 不够。写参数区时掉电会出现"新旧混合"，所以要 `StructCrc32` |
| "跳转就是把 PC 改一下" | 还要关中断、设 VTOR、换 MSP、加屏障。漏一样就可能在 App 里莫名 HardFault |

## 六、动手验证清单

**改一处、看一个现象** —— 这是把代码变成自己知识的最快方式。

| 改什么 | 预期现象 | 能验证什么 |
|---|---|---|
| `boot_app.h` 的 `BOOT_HOLD_WINDOW_MS` 改 0 | 上电不再等 1.5 秒，直接跳 App | 窗口逻辑 |
| 在 `BootApp_Decide` 第 ③ 步临时把期望地址改错 | 串口打印"账本里的 App 地址…不是期望的" | 决策链的前置条件 |
| 手动把参数区 `0x600000` 的前 4 字节改成 0x00 | 串口打印"参数区没有有效账本"，停在 Bootloader | 魔数的作用 |
| 把 `boot_param.c` 的回读校验注释掉，然后重新刷写 | 一样能成功（因为本来就不会失败）—— 说明它是**防御性**代码 | 为什么要防御 |
| `BOOT_BUILD_MODE` 改 `BOOT_BUILD_RELEASE`（在 `Library/build_cfg.h`），重新编译 | 串口只剩横幅和第 5~11 步的打印，帧细节消失 | 调试与业务的分离 |
| 刷完 App 后发 `11 01` | 串口打印"复位未生效，改为直接跳转 App"，然后 App 跑起来 | v1.7 的复位降级路径 |

> **注意**：前两项要重新编译烧录 Bootloader；后四项里的"发 11 01"可以直接用上位机试。

## 七、面试自测 8 问

答不上来的，回去读对应文件。

1. **Bootloader 怎么判断 App 是完整的？为什么要 7 步，只算 CRC 不行吗？**
   → 只算 CRC 也能拦坏内容，但 CRC 要读几十 KB（~400 ms）。前 6 步只读 8 字节，能用极低成本挡掉"空白/垃圾"，避免每次都白算 CRC。而且 CRC 只能证明"内容一致"，证明不了"这份内容本来就是个能跑的固件"（⑤⑥ 就是在检查向量表）。

2. **为什么参数区要存 CRC，直接存一个"有效"标志不行吗？**
   → 标志只能说明"上次流程走完了"，不能说明"内容没坏"。Flash 位翻转、写入不完整都可能让内容与预期不符。

3. **刷写到一半掉电，下次上电会怎样？**
   → 账本在擦除前就被置无效，所以上电第 ② 步就失败 → 停在 Bootloader → 可以重刷。**不会变砖**。

4. **跳转前要做哪几件事？为什么顺序不能乱？**
   → 关总中断 → 设 VTOR → 换 MSP（+dsb/isb）→ 跳。关中断必须在换栈之前（否则中断用旧 ISR + 新栈）；换 MSP 之后不能再碰内存。

5. **`msr msp` 之后为什么不能访问内存？**
   → 栈指针已经指向 App 的栈，Bootloader 的局部变量、参数都在旧的栈帧里，访问它们读到的是 App 栈上的垃圾。

6. **App 为什么必须把向量表放在自己起始地址？**
   → 我们设 `VTOR = AppStart`。如果 App 的向量表不在那儿，中断会取到错误的函数地址。

7. **`0x11 01` 的复位为什么要延迟 100 ms？**
   → `51 01` 这条正响应还在发送队列里。当场复位，诊断仪收不到响应，会判"复位失败"。

8. **如果上位机把 App 刷到了错误的地址（比如 0x600000），Bootloader 会怎么办？**
   → `dcm.c` 的 RequestDownload 会检查地址范围（NRC 0x31）；即使写进去了，账本里 `AppStart` 也是固定写 `FLS_APP_START`，第 ③ 步会拦住。
