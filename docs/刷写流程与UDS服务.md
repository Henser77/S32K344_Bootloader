# 一次完整刷写的 UDS 流程

> 对应固件：`v1.8` 　对应上位机：`D:\tools\uds_flash.py`
> 协议标准：ISO 14229-1（UDS 应用层）+ ISO 15765-2（CAN 传输层）

---

## 这份文档解决什么问题

刷写不是"发一个命令就把固件传进去"，而是**十个服务按固定顺序配合**，
每一步都有前置条件，任何一步的顺序错了都会被 ECU 拒绝（回 `7F` 负响应）。

本文按**真实执行顺序**逐个讲清楚：

- 这一步为什么必须有
- 请求的每一个字节是什么意思
- 正常的响应长什么样
- 前置条件被破坏时 ECU 回什么
- 本工程在哪个文件里实现
- 这一步掉电会怎样

---

## 零、全景

```
上位机                                     ECU（Bootloader）
  │                                            │
  │  ① 10 03   进入扩展会话 ─────────────────► │  允许做非默认会话的事
  │  ◄─────────────────────────── 50 03 00 32 01 F4
  │                                            │
  │  ② 27 01   请求种子 ─────────────────────► │  生成随机种子
  │  ◄───────────────────────────── 67 01 SS SS SS SS
  │                                            │
  │  ③ 27 02   发送密钥 ─────────────────────► │  校验 → 解锁
  │  ◄──────────────────────────────────── 67 02
  │                                            │
  │  ④ 10 02   进入编程会话 ─────────────────► │  允许刷写
  │  ◄─────────────────────────── 50 02 00 32 01 F4
  │                                            │
  │  ⑤ 31 01 FF00  擦除 App 区 ──────────────► │  先置账本无效，再擦
  │  ◄──────────────────────────── 7F 31 78      （要几秒，先回"请等待"）
  │  ◄───────────────────────── 71 01 FF 00 00
  │                                            │
  │  ⑥ 34 00 44 <地址4> <长度4>  请求下载 ────► │  检查地址/长度
  │  ◄────────────────────────────── 74 20 04 02
  │                                            │
  │  ⑦ 36 <块号> <1024 字节>  ×125 次 ───────► │  写入 Flash + 累加 CRC
  │  ◄───────────────────────────────── 76 <块号>
  │                                            │
  │  ⑧ 37 结束传输 ──────────────────────────► │
  │  ◄────────────────────────────────────── 77
  │                                            │
  │  ⑨ 31 01 FF01  校验 ─────────────────────► │  从 Flash 重算 CRC 对比
  │  ◄──────────────────────────── 7F 31 78
  │  ◄──────────────── 71 01 FF 01 00 <CRC32>  │  ★ 在这里写"App 有效"
  │                                            │
  │  ⑩ 11 01   复位 ─────────────────────────► │
  │  ◄──────────────────────────────────── 51 01
  │                                            │
  │                                    （复位/跳转 → App 跑起来）
```

**其中 ⑤ 和 ⑨ 是"两道门"**：一个负责"清干净"，一个负责"签收"。
没有 ⑨，账本永远是"无效"，上电不会跳 App。

## 一、先分清两层协议

刷写要同时用两套标准，它们**不是一回事**：

| 层 | 标准 | 负责 | 本工程模块 |
|---|---|---|---|
| 传输层 | **ISO 15765-2** | 把一条长报文拆成 8 字节的 CAN 帧（首帧/连续帧/流控帧）| `CanTp` |
| 应用层 | **ISO 14229-1 (UDS)** | 服务号、子功能、负响应码 | `Dcm` |

**对使用者来说只需要记住**：

```
CAN ID 0x7E0  ← 上位机发给 ECU
CAN ID 0x7E8  ← ECU 回给上位机
```

一条 UDS 请求超过 7 字节（单帧上限）时，CanTp 会自动拆成"首帧 + 连续帧"，
对方回一个"流控帧"表示可以继续。**这些在串口日志里能看到，但不需要手工处理。**

## 二、十个步骤逐个讲

### ① `10 03` —— 进入扩展会话

```
请求：10 03
响应：50 03 00 32 01 F4
```

| 字节 | 含义 |
|---|---|
| `10` | 服务号：DiagnosticSessionControl |
| `03` | 子功能：extendedDiagnosticSession（扩展会话）|

响应逐字节：

| 字节 | 含义 |
|---|---|
| `50` | `10 + 0x40` —— **正响应的规则是"服务号 + 0x40"** |
| `03` | 回显子功能 |
| `00 32` | **P2** = 0x0032 = 50 ms（收到请求后必须在 50 ms 内回响应）|
| `01 F4` | **P2\*** = 0x01F4 × 10 = 5000 ms（发过 `78` 之后可以再等 5 秒）|

**为什么不能直接进编程会话**：ISO 规定 `10 02` 必须先有扩展会话做跳板。
直接发 `10 02` 会被回 `7F 10 22`（conditionsNotCorrect）。

**本工程**：`dcm.c` 的 `Dcm_HandleSessionControl()`（第 397 行）。

**失败会怎样**：`7F 10 12`（子功能不支持）/ `7F 10 13`（长度错）。

---

### ② `27 01` —— 请求种子

```
请求：27 01
响应：67 01 SS SS SS SS          ← 4 字节种子
```

| 字节 | 含义 |
|---|---|
| `27` | 服务号：SecurityAccess |
| `01` | 子功能：**奇数 = 请求种子**（requestSeed）|

**注意**：奇数子功能代表"我要种子"，偶数代表"我送密钥"。`01` → 送密钥用 `02`。

**种子的作用**：防止重放。每次请求都不同（本工程用递增计数器生成）。

**实测**：`67 01 3B 92 DC 14` → 种子 = `0x3B92DC14`

**本工程**：`Dcm_HandleSecurityAccess()`（第 480 行）。

**一旦已解锁**：ISO 规定回**全 0 种子**（`67 01 00 00 00 00`），表示"不用再解锁了"。
这种情况下**不能**再发 `27 02`，否则会回 `7F 27 24`（requestSequenceError）。

> 这个坑实际踩过：上位机一开始见到 0 种子仍然发密钥，结果被拒。
> 现在 `uds_flash.py` 见到 0 种子会跳过第 ③ 步。

---

### ③ `27 02 KK KK KK KK` —— 发送密钥

```
请求：27 02 73 FC DC C6
响应：67 02
```

| 字节 | 含义 |
|---|---|
| `27` | SecurityAccess |
| `02` | 偶数子功能 = 发送密钥 |
| 后 4 字节 | 密钥（由种子算出来）|

**本工程的算法**（`Dcm_CalcKey`）：

```c
key = ((seed ^ 0x5A5A5A5A) + 0x12345678) & 0xFFFFFFFF;
```

> ⚠️ **这个算法不提供实际安全性**，只是把流程走通。
> 公式固定、种子用计数器生成，都能被反推。
> 真实产品要用 AES-128-CMAC + HSE 密钥区 + 硬件随机种子（见 `dcm.c` 里的注释）。

**常见负响应**：

| NRC | 含义 | 触发条件 |
|---|---|---|
| `0x24` | requestSequenceError | 没先请求种子就送密钥，或已解锁还送 |
| `0x35` | invalidKey | 密钥算错 |
| `0x36` | exceedNumberOfAttempts | 连续错太多次 |
| `0x37` | requiredTimeDelayNotExpired | 还在锁定延时里（本工程 10 秒）|

### ④ `10 02` —— 进入编程会话

```
请求：10 02
响应：50 02 00 32 01 F4
```

| 字节 | 含义 |
|---|---|
| `10` | DiagnosticSessionControl |
| `02` | programmingSession（编程会话）|

**进入编程会话后才允许**：`31 FF00`（擦）、`34`（下载）、`36`（传数据）、`37`。

**本工程的门槛检查**（`Dcm_HandleRequestDownload` 第 933 行等）：

```c
if (Dcm_SessionInProgramming() == FALSE) → NRC 0x7F（serviceNotSupportedInActiveSession）
if (Dcm_Security != UNLOCKED)           → NRC 0x33（securityAccessDenied）
```

这就是"**会话 + 安全**两道门"。

### ⑤ `31 01 FF00` —— 擦除 App 区

```
请求：31 01 FF 00
响应：7F 31 78              ← 先回"请等待"
      ...（约 400 毫秒）...
      71 01 FF 00 00        ← 再回正响应
```

请求逐字节：

| 字节 | 含义 |
|---|---|
| `31` | 服务号：RoutineControl |
| `01` | 子功能：**startRoutine** |
| `FF 00` | 例程 ID = **擦除存储器** |

响应逐字节：

| 字节 | 含义 |
|---|---|
| `71` | `31 + 0x40` |
| `01` | 回显子功能 |
| `FF 00` | 回显例程 ID |
| `00` | **例程状态**：`0x00` = 成功，非 0 = 失败 |

#### 为什么先回 `7F 31 78`

```
擦 1 MB 要 400 多毫秒
而诊断仪的 P2 超时只有 50 ms
   ↓
不先回点什么，诊断仪 50 ms 后就会判定超时 → 整个刷写失败
   ↓
所以先回 NRC 0x78（responsePending）
诊断仪收到 0x78 后把超时延长到 P2* = 5 秒
```

**顺序反了 = 诊断仪先超时 = 刷写失败。** 这是本模块最重要的一个细节
（`dcm.c` 第 706~723 行的注释写的就是它）。

#### 擦除时内部还做了一件关键的事

```c
if (BootParam_SetInvalid() != E_OK)      // ★ 先把账本标记成"App 无效"
{
    Dcm_SendNegative(..., NRC 0x72);     //   连记账都失败 → 不敢擦
    return;
}
// 然后才真正擦 Flash
```

**这是断电安全的核心**（详见 `boot_param.h` 文件头）：

```
擦除前先置"无效"  → 任何时候掉电，上电都看到"无效" → 停在 Bootloader → 可重刷  ✅
先擦再置"无效"    → 擦到一半掉电，账本还说"有效" → 跳进半擦的 App → 跑飞      ❌
```

#### 实测

```
擦除完成，用时 417 ms
[调试] 0x31 用时 417 毫秒，擦除 125 个扇区（8..132），
       轮询 2200000 次，重擦 0 次，最慢单扇区等待 4 毫秒
```

### ⑥ `34 00 44 <地址> <长度>` —— 请求下载

```
请求：34 00 44 00 50 00 00 00 00 7C 90
响应：74 20 04 02
```

请求逐字节：

| 字节 | 值 | 含义 |
|---|---|---|
| `34` | — | 服务号：RequestDownload |
| `00` | dataFormatIdentifier | `0` = 不压缩、不加密 |
| `44` | addressAndLengthFormatIdentifier | **高 4 位 = 长度占几字节（4），低 4 位 = 地址占几字节（4）** |
| `00 50 00 00` | memoryAddress | `0x00500000`（App 区起始）|
| `00 00 7C 90` | memorySize | `31888`（0x7C90）|

响应逐字节：

| 字节 | 值 | 含义 |
|---|---|---|
| `74` | — | `34 + 0x40` |
| `20` | lengthFormatIdentifier | 高 4 位 = 2 → 后面"最大块长度"占 **2 字节** |
| `04 02` | maxNumberOfBlockLength | **1026 字节**（含 2 字节头：`36` + 块号）|

**这条响应的意义**：ECU 在告诉你"每个 `36` 最多给我 1026 字节"。
所以上位机每块传 **1024 字节数据**（1026 − `36` − 块号）。

**地址检查**：如果地址不在 App 区范围内，回 `7F 34 31`（requestOutOfRange）。

---

### ⑦ `36 <块号> <数据>` —— 传输数据（重复 125 次）

```
请求：36 01 <1024 字节>
响应：76 01
```

| 字节 | 含义 |
|---|---|
| `36` | 服务号：TransferData |
| `01` | **blockSequenceCounter（块号）**，从 `0x01` 开始，每块 +1，`0xFF` 之后回到 `0x00` |
| 后面 | 数据 |

响应 `76 <块号>` 会把块号回显一遍 —— **上位机必须核对**，防止"响应错位"。

#### 三个必须遵守的规则

**① 块号必须连续**
如果 ECU 期望 `0x02` 却收到 `0x03`，回 `7F 36 24`（requestSequenceError）。

**② 每块长度不能超过 34 的响应里说的上限**
本工程 `DCM_MAX_BLOCK_LENGTH = 0x0402`，所以最多 1024 字节数据。

**③ 连续帧之间要留间隔**（本工程实测必需）
一段 1024 字节的数据会被 CanTp 拆成"1 个首帧 + 147 个连续帧"。
帧发太快，ECU 的单接收邮箱来不及重装 → 丢帧 → CanTp 发现序号错 → **直接中止且不回负响应**
→ 上位机只看到"等响应超时"。

> 这是最难查的一类问题：**ECU 那边什么都不说，上位机只看到超时。**
> 现在的参数是：**每块 256 字节 + 连续帧间隔 2 ms + 失败重试 3 次**。

#### 内部还在做一件事：累加 CRC

每收到一块，`Dcm` 就把它累加进 CRC32。这个值会在第 ⑨ 步和"从 Flash 读回来重算的值"比对。

---

### ⑧ `37` —— 结束传输

```
请求：37
响应：77
```

没有参数。作用是告诉 ECU"数据发完了"。

**如果没发 `37` 直接发 `31 FF01`**：ECU 可能还在等数据，回 `7F 31 24`。

### ⑨ `31 01 FF01` —— 校验（并写"App 有效"）

```
请求：31 01 FF 01
响应：7F 31 78
      ...（约 400 毫秒，要读 31888 字节算 CRC）...
      71 01 FF 01 00 58 1C 35 5A
                    └┬┘ └────┬────┘
                 状态=成功   CRC32 = 0x581C355A
```

请求逐字节：

| 字节 | 含义 |
|---|---|
| `31` | RoutineControl |
| `01` | startRoutine |
| `FF 01` | 例程 ID = **校验完整性** |

响应多了 4 字节 CRC（这是"例程结果"，因为响应长度是变长的）。

#### 这一步最关键：它是唯一"签收"的地方

```c
crcRead = 从 Flash 重新算整个 App 区          // 不是用下载时累加的那个
if (crcRead == 累加值) {
    BootParam_SetValid(AppSize, crcRead);    // ★ 写账本：AppValid = 1
}
```

**为什么用"从 Flash 重算"的值**：账本的语义是"Flash 里现在是什么"，
不是"我以为我写进去了什么"。写入如果有静默错误，两者会不同。

#### CRC 不一致会怎样

回 `7F 31 72`（generalProgrammingFailure），且**账本保持"无效"** ——
上电会停在 Bootloader，可以重刷。**绝不会跳进坏固件。**

#### 一个容易忽略的设计

```c
if (Dcm_DownloadStart == DCM_DOWNLOAD_START_ADDR)   // 只有从 0x500000 开始才记账
{
    BootParam_SetValid(...);
}
```

如果诊断仪把固件下到 App 区中间的某个地址，**不记账** ——
因为上电校验会从 `0x500000` 开始算 CRC，那种情况必然对不上。

### ⑩ `11 01` —— 复位

```
请求：11 01
响应：51 01
```

| 字节 | 含义 |
|---|---|
| `11` | 服务号：EcuReset |
| `01` | 子功能：hardReset（硬复位）|

**为什么复位动作不能在这个服务里当场做**：

```
51 01 这条正响应还在发送队列里
当场复位 → 诊断仪收不到响应 → 判"复位失败"
   ↓
所以 Dcm 只置一个标志，由 EcuM_MainFunction 等 100 ms 后再执行
```

#### 本工程的实际行为（S32K344 特殊性）

**AirCR 那条路在 `S32K344` 上实测无效**（写 `AIRCR.SYSRESETREQ` 后该位一直保持 1，芯片不动），
  真正的软件复位要走 **MC_ME**（NXP 官方 `Mcu_PerformReset` 就是这么做的）：

  ```c
  MC_ME->MODE_CONF = FUNC_RST;   /* ① 要做什么 */
  MC_ME->MODE_UPD  = 1;          /* ② 提交 */
  MC_ME->CTL_KEY   = 0x5AF0;     /* ③ 写钥匙 —— "启动硬件动作" */
  MC_ME->CTL_KEY   = 0xA50F;
  ```

  ⚠️ **这三步的顺序不能变**：钥匙必须写在最后。写在前面会导致
  "启动信号发出时配置还是空的"，配置之后又没人再启动它 —— 表现就是
  "什么都不发生"。本工程正是踩了这个坑（v1.12 → v1.13 修正）。
所以现在的降级路径是：

```
等 100 ms → 请求复位 → 等 50 ms
   ├─ 复位成功：芯片重启（走不到下面）
   └─ 没复位：清标志 → 重新校验 App 的 CRC
                ├─ 通过 → 停 CAN → 直接跳转 App   ★ 刷完 0.5 秒后 App 自己跑起来
                └─ 不通过 → 留在 Bootloader
```

详细实验记录见提交 `15f3255`（发现）和 `3172888`（降级方案）。

### 附：`31 01 FF 03` / `31 01 FF 04` —— "下次上电留在 Bootloader"的门铃

**这两个不在刷写主流程里**，是 v1.16 新增的"入口管理"。

#### 为什么需要它

发布版把启动窗口缩到 1 秒（甚至想设成 0）。窗口一过，板子就跳去跑 App 了。
想连着刷好几次，每次都去"断电 + 抓窗口"很痛苦。

更严重的场景：**如果窗口设成 0、而 App 又是好的，软件上就再也进不去 Bootloader 了**
（2026-10-25 实测踩到：现象是"看起来 Bootloader 没了"，只能上 J-Link 救）。

#### 怎么工作

```
诊断仪：31 01 FF 03
ECU  ：往参数区账本写 BootRequest = 1（擦+写一个扇区，约 3.4 ms）
诊断仪：11 01
ECU  ：复位
上电  ：Bootloader 读到 BootRequest = 1
          -> 清掉它（只消费一次）
          -> 不跳 App，留在 Bootloader 等刷写
```

**为什么存 Flash 而不是 RAM**：要扛得住断电。
"我要刷固件"这个意图不能因为掉电就丢了。

#### 和 `0xFF02` 的区别

| 例程 | 性质 | 发布版 |
|---|---|---|
| `0xFF02` 信任当前 App 区 | **调试后门**（不验货就签收）| 关闭 |
| `0xFF03` / `0xFF04` 门铃 | **正式功能**（管理启动去向）| 保留 |

#### 上位机命令

```bat
:: 按下门铃 + 立即复位，之后就一直留在 Bootloader 里
uds_flash.py --request-boot

:: 取消门铃，下次上电正常跳 App
uds_flash.py --clear-boot
```

#### 账本字段的变化（向后兼容）

`Boot_ParamType` 里原来的 `Reserved0` 改名为 `BootRequest`：

```
Magic / AppValid / AppStart / AppSize / AppCrc32 / BootRequest / Reserved1 / StructCrc32
                                                    ^ 只改名字，布局仍是 8 x uint32 = 32 字节
```

`Reserved0` 一直是 0，正好等于"没有请求" —— 所以**老账本读出来自动就是无请求**，
不需要任何迁移。

## 三、贯穿全程的两个"背景服务"

### `3E 00` —— TesterPresent（保活）

```
请求：3E 00
响应：7E 00
```

**作用**：告诉 ECU"我还在，别把会话超时退回去"。

**为什么要它**：非默认会话有 **S3 超时**（本工程手工测试模式 120 秒，标准 5 秒）。
超过 S3 没收到任何请求，ECU 会自动退回默认会话 —— 那时 `36`/`37` 都会被拒。

**写变体 `3E 80`**：子功能 bit7（`0x80`）= **suppressPosRspMsgIndicationBit**（抑制正响应），
表示"收到了就行，别回我"，用来减少总线负载。

**本工程的 S3 配置**（`dcm_cfg.h`）：

```c
#define DCM_S3_MS   (120000U)   /* 手工测试模式：2 分钟 */
#define DCM_S3_MS   (5000U)     /* 标准：5 秒 */
```

---

### `7F` —— 负响应格式

```
7F <服务号> <NRC>
```

三个字节永远是：

| 字节 | 含义 |
|---|---|
| `7F` | 负响应固定前缀 |
| 第二个 | **原始请求的服务号**（不是 +0x40）|
| 第三个 | NRC 负响应码 |

例：`7F 27 24` = "你发的 27 服务，被拒绝，原因是 requestSequenceError"。

**`7F xx 78` 是特殊的**：它不是"失败"，而是"**我还在干，别超时**"。
收到 `78` 之后要继续等，超时按 P2\*（5 秒）算。

---

## 四、本工程实际会回的 NRC

| NRC | 名称 | 什么时候 |
|---|---|---|
| `0x10` | generalReject | 兜底 |
| `0x11` | serviceNotSupported | 不支持的服务号 |
| `0x12` | subFunctionNotSupported | 子功能不对 |
| `0x13` | incorrectMessageLengthOrInvalidFormat | 长度不对 |
| `0x22` | conditionsNotCorrect | 比如直接 `10 02` 没先 `10 03` |
| `0x24` | requestSequenceError | 块号不连续 / 没请求种子就送密钥 / 已解锁还送密钥 |
| `0x31` | requestOutOfRange | `34` 的地址不在 App 区 |
| `0x33` | securityAccessDenied | 没解锁就调 `31`/`34` |
| `0x35` | invalidKey | 密钥算错 |
| `0x36` | exceedNumberOfAttempts | 连续错太多次 |
| `0x37` | requiredTimeDelayNotExpired | 还在锁定延时（10 秒）里 |
| `0x72` | generalProgrammingFailure | 擦/写 Flash 失败 |
| `0x78` | responsePending | **不是错误**：请再等 |
| `0x7E` | subFunctionNotSupportedInActiveSession | 子功能在当前会话不可用 |
| `0x7F` | serviceNotSupportedInActiveSession | 服务在当前会话不可用 |

## 五、断电安全：每个时刻掉电会怎样

| 时刻 | 掉电后上电 | 能否恢复 |
|---|---|---|
| ①~④（会话/解锁阶段）| 参数区没动，App 完好 | ✅ 直接跳 App（走启动窗口）|
| **⑤ 擦除中** | 账本已置"无效" → **停在 Bootloader** | ✅ 重刷即可 |
| ⑥~⑧（下载中）| 账本仍是"无效" → 停在 Bootloader | ✅ 重刷即可 |
| **⑨ 校验中** | 账本还是"无效"（`SetValid` 还没执行）| ✅ 重刷即可 |
| ⑨ 之后、⑩ 之前 | 账本已"有效" | ✅ 上电跳 App（这次的固件是完整的）|
| ⑩ 之后 | — | ✅ |

**整条流程从头到尾，没有任何一个时刻会让板子"变砖"。**

核心只有一条：**"有效"这个标记，永远是最后一步才写。**

## 七、为什么顺序不能变（ISO 的硬约束）

| 约束 | 原因 |
|---|---|
| `10 03` 必须在 `10 02` 之前 | ISO 规定进编程会话前必须先处于扩展会话 |
| `27` 必须在 `10 02` 之前或之后皆可，但**必须在 `31`/`34` 之前** | 擦写 Flash 要求已解锁 |
| `31 FF00`（擦）必须在 `34` 之前 | 没擦就写 = 写到有数据的单元上（Flash 只能 1→0）→ 数据错 |
| `34` 必须在 `36` 之前 | `36` 依赖 `34` 建立的下载上下文（地址、剩余长度）|
| `36` 的块号必须从 `01` 开始且连续 | ISO 15765-2 / 14229-1 的流控要求 |
| `37` 必须在最后一帧 `36` 之后 | 表示数据结束 |
| `31 FF01`（校验）必须在 `37` 之后 | 要等所有数据落盘才能算 CRC |
| `11 01` 必须在 `31 FF01` 成功之后 | 否则账本没写，复位后还是停在 Bootloader |

## 八、上位机命令 ↔ 服务对照

| 上层动作 | 内部发的服务序列 |
|---|---|
| `--probe`（测试连接）| `3E 00` |
| `--wait N`（等板子上电）| 循环 `3E 00` |
| `--erase-only` | `10 03` → `27 01/02` → `10 02` → `31 01 FF00` |
| `--image app.elf` | ①~⑩ 全部 |
| `--image --no-erase` | 跳过 `31 01 FF00` |
| `--image --no-verify` | 跳过 `31 01 FF01`（**不推荐**：账本不会写"有效"）|
| `--image --no-reset` | 跳过 `11 01` |
| `--dry-run` | 一个帧都不发，只解析 ELF |

## 九、常见误区

| 误区 | 事实 |
|---|---|
| "发 `34` 就能传数据了" | 还要 `36` 一块一块传，且块号必须连续 |
| "`37` 之后刷写就完成了" | **没有**。必须 `31 FF01` 写账本，否则上电不跳 App |
| "CRC 一致就说明写对了" | 对，但这个"CRC"是**ECU 从 Flash 重算的**，不是上位机自己算的 |
| "`7F` 一定是失败" | `7F xx 78` 是"请等待"，要继续等 |
| "会话不用管，直接发命令" | 每个服务都有前置会话要求，错一步就 `7F` |
| "块越大越快" | 块越大 → 连续帧越多 → 丢帧概率越大。本工程从 1024 降到 256 才稳定 |
| "擦除完 App 区就空了，上电肯定停 Bootloader" | 对，但前提是账本已被置"无效"（擦除前做的）|
